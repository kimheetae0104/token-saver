# 토큰 세이버 가이드 (상세 근거)

> 이 문서는 **자동 로드되지 않는다**(반복 토큰 비용 0). 규칙의 *이유·수치·경계*를 담는 참고서다.
> 강제 규칙 요약은 [../CLAUDE.md](../CLAUDE.md), 측정 도구는 [../measure.py](../measure.py).

## 0. 북극성 — 왜 "절약 vs 품질"이 가짜 트레이드오프인가

대부분의 경우 토큰을 줄이면 **싸지고 동시에 좋아진다**. 근거:
- **context rot**: 입력이 길수록 모든 프런티어 모델의 정확도가 한계 훨씬 전에 떨어진다. 노이즈 토큰은 비용이자 품질 저하 요인.
- **장황함 ≠ 품질**: 출력 길이와 성공률은 약한 음의 상관. 간결 제약이 오히려 정확도를 최대 +26%p 올린 연구도 있다(scale-dependent verbosity 오류 제거).

따라서 목표는 "토큰 최소화"가 아니라 **신호 밀도(signal density) 극대화** — 노이즈만 깎고 신호는 보존.
둘이 갈라지는 **유일한 경계**: 필요한 추론 단계까지 자를 때. → 최종 답은 짧게, 필요한 추론은 확보.

측정 함의: `measure.py`는 비용만이 아니라 value-per-token / 신호비율을 본다. "최소화만"을 좇으면
"아무것도 안 하기"가 최적해가 되는 함정에 빠진다.

## 1. 비용 구조 (5분면) — measure.py 가격표의 근거

하나의 요청은 최대 5종 단가로 과금된다:

| 축 | base input 대비 | 비고 |
|---|---|---|
| base input(비캐시) | 1.0× | |
| 5분 cache write | 1.25× | 5분 TTL |
| 1시간 cache write | 2.0× | 1시간 TTL |
| cache read | 0.1× | 90% 할인 |
| output | 5× (= base×5) | 생성 토큰 |

비용 함수:
```
cost = input×b + cc_5m×b×1.25 + cc_1h×b×2 + cache_read×b×0.1 + output×b×5
```
모든 모델에서 배수가 일정 → **모델별 base input 단가 하나**만 알면 나머지는 파생.

**가격표(base input $/MTok, 2026-08; 런타임 재확인 권장)**: Haiku 4.5 $1 · Sonnet 5 $2(2026-09-01부터 $3)
· Opus 4.5~5 $5 · Fable 5 $10.

**주의**: `usage.input_tokens`는 "마지막 캐시 브레이크포인트 이후 비캐시분"만 담는다.
**총 입력 = input + cache_creation + cache_read** 를 반드시 합산.

## 2. 프롬프트 캐싱 — 가장 큰 숨은 레버

- **손익분기**: 5분 캐시는 재사용 1회, 1시간 캐시는 2회부터 이득. 히트 시 TTL 무료 갱신.
- **무효화 트리거(피할 것)**: `/model`·`/effort`·`/fast` 변경, MCP 연결/해제, `/compact`, 도구 정의 변경,
  버전 업 후 첫 턴. → **세션 시작 시 모델·effort 고정 후 유지.**
- **캐시 친화 구조**: 안정적 접두부(툴 정의→system→문서)를 앞, 동적(사용자 메시지)을 뒤.
- **컨텍스트를 굶기지 말고 캐시하라**: 목표는 작은 컨텍스트가 아니라 "재계산 비용이 작은 훌륭한 컨텍스트".
  훌륭한 컨텍스트를 1회 write 후 0.1× read로 재사용.

## 3. 구독(Pro/Max/Team) 특화

- per-token 청구가 아니다 → 진짜 제약은 **5시간/주간 롤링 사용 한도**. $는 "동등 API 비용" 참고치.
- **캐시 자동 1시간 TTL** → 긴 세션 유지 + 접두부 재사용이 유리. 새 세션 남발 = cold write 반복(손해).
- 판단 기준: 컨텍스트가 커지고 남은 작업이 작을 때만 `/clear`. 그 외엔 유지가 이득.

## 4. 상황별 규칙

**탐색**: grep으로 위치 먼저 → Read는 offset/limit. 통독 금지. 큰 도구 출력은 head/grep/wc로 좁힘.
**위임**: 대량 탐색·검증·파싱은 서브에이전트(격리 캐시, 요약만 회수). trivial은 배치(cold-start 때문).
**왕복**: 독립 도구 병렬. 계획-후-실행. 재확인 반복 금지.
**출력**: diff/요점, 서론·맺음말 제거, 끝나면 정지. 필요 추론은 확보.
**모델/effort 사다리**: 값싼 오라클 있으면 Haiku/low로 시작→검증→실패시 상향. 오라클 없고 고위험이면 처음부터 상위.
**thinking 예산**: thinking 토큰은 output 단가(base×5)로 과금 → effort high의 확장 사고는 비싸다. 기계적 작업에 high면 5× 낭비(실험2·4 관측). 세션 중 전환은 캐시 무효화 주의.
**지시문 포맷(구조화)**: 짧은 flat list(4슬롯류)는 Markdown 확정(실험21, N=20 — 컴플라이언스 동률 최고+토큰 최저, `hooks/prompt_gate.py`에 적용됨). 소규모 구조 콘텐츠(엔티티 수십 개 이하)는 포맷 무관(실험22, 천장 효과). 규모가 커지면(엔티티 30개대) **HTML만 먼저 정확도가 무너짐**(실험23, 90% vs 나머지 100%) — 큰 구조 콘텐츠를 모델에 먹여야 할 기능을 새로 만들 땐 HTML을 피하고 XML/Markdown을 기본값으로. JSON은 구조 데이터 정확도는 다른 포맷과 동률이지만 자유텍스트 확인 과제(4슬롯류)에선 96.3%로 근소 최하위(실험23) — 코드가 그대로 파싱할 구조화 출력엔 적합해도 사람이 읽는 프롬프트형 지시문 대체용으로는 권장 안 함. 근거·수치: `experiments/PROTOCOL.md` 실험21~23.

## 5. 측정 방법론 — value-per-token

분모(토큰)는 정확, 분자(품질)가 난제. 2층으로 분리한다.

**① 라이브 층(정답 불필요, 로그 관측)** — `measure.py`가 산출:
- step_efficiency(>1.3 경보), read_thrash, parallelism, ctx_growth, correction_ratio, clarify, verbosity, cache_hit.
- 종합 효율 점수 0–100 = f(캐시적중, 병렬, 1−backtracking, 1−correction).

**② 실험 층(통제 A/B에서만)**:
- **OckScore**: `Quality − λ·ln(AvgTokens/T0 + 1)`. 토큰 과소비를 로그 페널티.
  ⚠️ **AvgTokens는 태스크당 토큰**이지 세션 전체 누적이 아니다(누적을 넣으면 값이 무의미).
- quality_per_1k = Quality / (Tokens/1000). 비용축은 재현성 위해 토큰 우선, $는 파생.
- 신뢰도: pass@1 + **pass^k**(k회 전부 성공). 리포트는 Pareto frontier(Quality vs Tokens) 위 점만.
- 주관 품질 심판: **길이통제 win-rate(AlpacaEval 2.0 LC)** + pairwise + 순서 랜덤화 + swap augmentation +
  자기모델 심판 금지(교차/앙상블) + 인간 100~300건 κ>0.6 보정. (순진한 judge는 긴 답 선호 → 우리 주제 배신)

근거: MT-Bench(2306.05685), AlpacaEval-LC(2404.04475), OckBench, Token Complexity(2503.01141).

## 6. 검증 루프 (rework 방지 = 품질×비용 win-win)

- **결정 규칙**: P(오류)×비용(rework+나쁜결과) > 비용(검증)일 때만. 고레버리지 게이트(완료·커밋·전송 직전).
- **값싼 오라클부터**: ①결정론(compile/lint/test/schema) → ②자기일관성(k회 다수결) → ③독립 LLM 검증자
  (값싼 모델·새 컨텍스트·**적대적** "틀린 곳을 찾아라") → ④인간(최고 stakes만).
- **독립 검증 > 자기성찰**(자기비평은 생성기 맹점 공유). 검증자 = 격리 컨텍스트 새 서브에이전트.
- 루프 상한 2~3회(수확체감).

## 7. "안전하게 줄여도 되는 것 vs 줄이면 품질 상하는 것"

| 안전하게 줄여도 됨 (품질 유지/개선) | 줄이면 품질 상함 (주의) |
|---|---|
| 역할 끝난 raw 도구 결과·중복 출력 | 짧은 컨텍스트를 더 압축(버릴 노이즈 없음) |
| 출력의 서론·맺음말·헤징 | 과도한 압축 → hallucination |
| 질문과 무관한 검색 청크(query-aware) | 코드/구조화 데이터의 토큰 단위 프루닝(구문 파손) |
| 시스템 프롬프트의 엣지케이스 나열(→정규 예시 소수로) | 대화 이력의 무분별 프루닝(연속성·미래 의존 손실) |
| | 추론 단계 과잉 간결화(수학 등 최대 ~28% 하락) |

## 8. 시스템·행동 레버

- **사용자 코칭**: 토큰 최대 변수는 프롬프트 습관(모호·방향전환·선행 컨텍스트 부족). 타이트하게 쓰기.
- **세션 간 상각**: 반복 작업은 스킬로 encode, Opus 1회 증류→값싼 재사용, 코드베이스 맵 외부 저장.
- **지속 개선**: measure/부검 → 규칙 인코딩 → 재측정. 단 학습=축적이 아니라 **증류+가지치기**(쌓기만 하면 rot).
- **스킬 vs 프롬프트**: 반복·복잡 → 스킬(상각·일관·온디맨드 로드), 일회성 → 프롬프트. 안 쓰는 스킬 큐레이션.
- **세션 분산**: "운 좋은 서버" 로또는 거의 없음. 분산은 샘플링·컨텍스트/캐시 상태에서. 자기일관성·검증으로 통제,
  measure로 골든 세션 선별 후 산출물 증류.
- **언어 비용**: Claude는 네이티브 다국어 → 별도 번역 단계 없음. 한국어가 의미당 토큰↑. 정리/번역 레이어 추가는
  대개 순손해(AI-YAGNI). 자가 영어번역보다 "타이트하게 쓰기"가 정답.

## 10. measure.py 사용법

```bash
python3 measure.py                 # 최신 세션 리포트 + 부검
python3 measure.py --autopsy       # 낭비 부검만
python3 measure.py --diff A B      # 두 세션 비교
python3 measure.py --all           # 세션 간 추세
echo '{"transcript_path":"..."}' | python3 measure.py --statusline
python3 measure.py --score --quality 0.9 --tokens 8000   # 태스크당 토큰!
```
가격표·임계값은 파일 상단 `BASE_IN`·`THRESH`에서 조정. 실제 단가는 공식 pricing 페이지로 재확인.
