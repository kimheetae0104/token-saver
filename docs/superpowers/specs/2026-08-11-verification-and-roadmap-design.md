# 검증 → 로드맵 설계 (2026-08-11)

## 배경
18차 세션(HANDOFF.md)까지 실험21~23과 문서 승격이 끝난 상태에서, 사용자가 "계획 세우고
로드맵 세워서 토큰 세이버 기능 강화 및 다른 아이디어들로 더 디벨롭할 수 있는 것이
있는지, 아니면 지금까지 결과물로 테스트 검증해보든가 해봐"라고 요청. 브레인스토밍으로
범위를 좁힌 결과, **B(기존 결과물 검증)를 먼저 하고 A(기능 강화·신규 아이디어)는 그
다음**으로 순서를 확정했다. A는 이번 세션에서 "아이디어 목록+우선순위"까지만 산출하고
실제 구현은 다음 세션으로 미룬다.

## 목적
1. 지금까지 만든 8개 hooks·MCP 서버·measure.py·문서(README/HANDOFF/TOKEN-GUIDE/PROTOCOL)가
   실제로 정확한지, 서로 정합적인지, 실사용에서 효과가 있는지 이번 세션 안에서 재확인하고
   발견된 문제는 바로 고친다.
2. 그 결과를 근거로 다음에 개발할 만한 기능·개선 아이디어를 우선순위와 함께 정리해
   다음 세션이 바로 착수할 수 있게 한다.

## 범위
- **포함**: 테스트 스위트 재실행, `claude plugin validate`, 문서-코드 정합성 감사(README/
  HANDOFF/TOKEN-GUIDE/PROTOCOL 대상), `measure.py`를 통한 최근 세션 재측정, 발견된 문제의
  즉시 수정, 아이디어 목록+우선순위 산출.
- **제외**: Phase 2에서 나온 아이디어의 실제 구현(다음 세션), 블로그 관련 요청(다른
  프로젝트로 확인됨, 이 스펙과 무관), 대규모 멀티에이전트 Workflow 오케스트레이션(사용자가
  명시 요청 안 함 — 이번 범위는 일반 서브에이전트 위임까지만).

## Phase 1 — 검증 (순차: 코드건강성 → 정합성 → 실사용효과)

### 1-1. 코드 건강성
방법: 직접 실행(결정론적 명령이라 위임 불필요).
- `pytest`(또는 프로젝트가 실제 쓰는 러너) 전체 스위트 — 현재 문서 주장(215/215) 재확인.
- `claude plugin validate`.
- `hooks/hooks.json` 배선과 실제 파일 존재 여부 대조(누락·오타 배선 탐지).

실패 발견 시: 이번 세션에서 즉시 수정(rework 방지 원칙 — 검증 단계에서 발견된 회귀는
다음 단계로 넘기지 않는다).

### 1-2. 문서 vs 코드 정합성 감사
방법: 문서당 서브에이전트 1개 병렬 위임(대량 스윕 성격, 결론만 회수).
- 대상: `README.md`/`README.en.md`, `HANDOFF.md`, `docs/TOKEN-GUIDE.md`,
  `experiments/PROTOCOL.md`.
- 각 문서의 구체적 주장(수치·임계값·"N/N 통과"·버전 배지·"현재 적용됨" 같은 상태 서술)을
  추출해 현재 코드(`hooks/*.py`의 THRESH 상수, `config_store.py` DEFAULTS, 실제 테스트
  카운트, `plugin.json`/`marketplace.json` 버전)와 대조, 불일치 목록만 반환.
- 우선 확인 대상(이미 알려진 위험 지점): `many_agents=12`(outlier 1건 기반, 세션 누적
  대기 상태로 문서화됨 — 재보정 여부 판단), README 버전배지/테스트뱃지, TOKEN-GUIDE §4
  승격 규칙 표현이 실제 훅 코드(`prompt_gate.py` 등) 동작과 일치하는지.

발견된 불일치는 이번 세션에서 바로 정정(문서 수정 or 코드 수정, 어느 쪽이 진실인지
판단 후).

### 1-3. 실사용 효과 재측정
방법: 직접 `measure.py --all --autopsy` 실행(기존 도구 재사용, 위임 불필요).
- 최근 세션(18차 이후 누적분 포함) 대상으로 hook 실제 발화 빈도, 에스컬레이션률,
  ladder_gate 추천/실제 티어 일치율 등 문서가 인용하는 수치를 재계산.
- 표본이 여전히 작아 결론이 안 바뀌면 "표본 부족, 판단 보류"로 정직히 기록(기존 HANDOFF
  관행과 동일 — 억지로 결론 내지 않음).

### Phase 1 산출물
- 회귀 수정, 문서-코드 불일치 정정, 수치 갱신 — 별도 리포트 파일을 새로 만들지 않고
  실제 파일(코드/문서)을 직접 고치는 방식.
- 큰 발견(반증된 임계값, 재현된 결함 등)은 HANDOFF.md에 새 세션 항목(19차)으로 기록.

## Phase 2 — 개발 아이디어 목록 + 우선순위

### 소싱 3갈래
1. **Phase 1 실측 근거**: 검증 중 실제로 드러난 갭(문서-코드 불일치, 재현된 결함, 표본
   부족으로 판단 보류된 항목) — 가장 신뢰도 높은 소스.
2. **HANDOFF.md 기존 열린 스레드**: many_agents 재보정, verify_fails 재검증, 병렬 haiku
   겹침 등 — Phase 1-3 재측정으로 상태가 바뀌었으면 갱신, 안 바뀌었으면 "여전히 데이터
   대기"로 유지.
3. **신규 가설 아이디어**: 아직 코드에 없는 것(다른 라우팅 신호, MCP 툴 확장, Desktop/
   Windows 격차 완화 등) — 실측 근거가 없으므로 "가설" 딱지를 붙여 1·2와 구분.

### 항목 기록 형식
설명(1줄) · 가치(왜 필요) · 예상 비용(구현 난이도) · 블로커 유무 · 소스(1/2/3).

### 우선순위 산식
가치/비용 비율을 기본으로 하되, 프로젝트 자체 원칙(AI-YAGNI, 오라클 없는 소표본은 실측
금지)에 위배되는 항목은 "제외 사유"와 함께 리스트에서 뺀다 — 뺀 이유도 남겨야 다음 세션이
같은 아이디어를 다시 꺼내지 않는다.

### Phase 2 산출물
- 이 스펙 문서 하단(또는 별도 섹션)에 우선순위 표로 정리.
- `HANDOFF.md` "열린 스레드" 섹션을 이 표 기준으로 갱신 — 구현은 하지 않고, 다음 세션이
  표에서 골라 시작할 수 있는 상태로만 만든다.

## 성공 기준
- Phase 1: 테스트 스위트 결과가 문서 주장과 일치하거나, 불일치가 전부 정정됨.
- Phase 1: 감사 대상 4개 문서에서 발견된 불일치가 전부 처리(수정 또는 "의도적 차이"로
  명시)됨.
- Phase 2: 우선순위 표가 존재하고, 각 항목에 소스·가치·비용·블로커가 채워짐.

## 리스크·오픈 이슈
- 1-3(실사용 재측정)은 세션 누적량에 따라 "판단 보류"로 끝날 수 있음 — 이는 실패가
  아니라 프로젝트의 "실측만 기록" 원칙에 따른 정상적 결과.
- 문서-코드 불일치가 발견됐을 때 "어느 쪽이 진실인지"가 항상 명확하진 않을 수 있음 —
  불명확하면 코드 실행 결과를 우선 진실로 삼는다(문서는 코드를 서술하는 것이 원칙).
