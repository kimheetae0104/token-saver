# 부품별 끄기 실험(ablation) — 설계 스펙 (2026-10-12)

## 목적
token-saver는 하네스(모델을 뺀 나머지 전부) 안의 한 부품 묶음이다. 하네스 설계 글들의
공통 권장은 "부품마다 모델이 혼자 못 하는 것에 대한 가정이니, 하나씩 빼 보고 필요한 것만
남겨라"다(Anthropic, Harness design for long-running application development, 2026-03-24).
지금 token-saver 부품 가운데 **켜고 끈 비교로 효과를 잰 것은 일부뿐**이고(아래 표), 몇몇은
매 턴 컨텍스트에 글을 넣어 그 자체가 비용이다. 이 스펙은 부품마다 "꺼도 비용·정답이
그대로인가"를 같은 과제로 재서 남길 것과 뺄 것을 가르는 실험을 정한다.

판정 기준은 CLAUDE.md 북극성과 같다: 토큰만이 아니라 **토큰당 아웃풋**. 그래서 모든 조건에서
비용과 함께 정답 여부(오라클 통과)를 잰다. 정답률이 떨어지는 절감은 절감으로 치지 않는다.

## 범위 밖(의도적)
- 부품을 실제로 지우거나 기본값을 바꾸는 일 — 결과가 나온 뒤 별도 PR에서 한다.
- Claude Code 내장 라우팅(스킬·서브에이전트 설명 문구, 서브에이전트 `model` 칸) 자체의 성능
  평가 — 이 스펙은 token-saver가 그 위에 더하는 값만 잰다.
- 새 측정 지표 — 기존 `measure.py`의 비용 5분면, 캐시절감 $, 효율점수, 오라클 통과를 그대로 쓴다.

## 실험 설계
조건은 **전부 켬(현행)**, **전부 끔**, 그리고 **하나만 끔** 7개(위 표에서 autopsy 제외, trim 둘은
묶음)로 총 9개다. 매 턴 주입 부품(intent_gate, habit_coaching, measure --check)은 config 스위치가
없으므로 1단계로 `config_store.DEFAULTS`에 `disabled` 키를 더한다(기본 False, 동작 변화 없음,
테스트 추가).

과제는 기존 자산을 다시 쓴다: 오라클 있는 `experiments/ladder_real` 과제와 `fixtures/`의
대형 파일 탐색 과제(webapp, big_module.py, service.go). 오라클 없는 과제는 정답 판정이
흔들리므로(실험9·14) 이번에는 제외한다.

반복 수는 실험19의 교훈대로 파일럿 N=5로 방향만 보고, 차이가 보이는 조건만 N을 늘린다.
조건당 N=5 × 9조건 = 45회가 파일럿 상한이다. 각 실행은 새 세션(캐시 조건 동일화)이고
모델·effort는 고정한다.

## 지표와 판정
- 주: 과제당 비용($, 5분면), 오라클 통과율
- 보조: 도구 호출 수, 왕복 수, 매 턴 주입 글자 수(주입 부품의 순수 컨텍스트 비용)
- 판정: 하나만 끈 조건이 "전부 켬" 대비 **비용 차이가 신뢰구간 안이고 통과율이 같거나 높으면**
  그 부품은 제거 후보. 통과율이 떨어지면 남긴다. 비용이 줄고 통과율도 떨어지면 사용자 판단.

## 단계
1. 스위치 없는 3개 부품에 config `disabled` 추가 + 테스트 (`pytest` 통과 확인)
2. 매 턴 주입 글자 수 실측 — 완료(실험 24). 세 부품 합쳐 사람 턴당 약 64자로 무시할 만해,
   이 부품들은 3단계에서 주입 비용이 아니라 행동 변화(왕복 수·정답률)로 판정한다
3. 파일럿 45회 실행 → PROTOCOL.md에 실험 25로 기록(2단계 결과는 실험 24)
4. 제거 후보 목록과 근거를 사용자에게 보고, 실제 제거는 별도 PR
