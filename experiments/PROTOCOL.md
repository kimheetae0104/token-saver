# 실험 프로토콜 — baseline vs optimized 실측

목적: 절약 전략의 효과를 **지어내지 않고 실제로 측정**해 비교한다. 비용축은 하네스가 계측한 토큰.

## 절차
1. **동일 과제**를 하나 정한다(정답이 검증 가능한 것 우선).
2. 두 조건을 **각각 새 서브에이전트/세션**에서 실행:
   - **Baseline(비효율)**: 파일 통독, 장황한 출력.
   - **Optimized(효율)**: grep-first + offset/limit, 간결 출력.
3. 토큰은 **하네스 실측치**로 기록(서브에이전트: task-notification의 `subagent_tokens`;
   세션: `python3 measure.py --diff A B`).
4. **정답 일치(품질)를 반드시 검증** — 토큰만 줄고 품질이 깨지면 무의미.
5. `python3 measure.py --score --quality Q --tokens N` 으로 OckScore·quality/1k 계산.
   ⚠️ 여기서 tokens는 **과제당 토큰**(세션 전체 누적 아님).

## 결과 기록 (실측 — 지어낸 값 없음)

### 실험 1 — "캐시 무효화 유발 요인 6개 찾기" (2026-08-01)
대상 파일: `measure.py`, `CLAUDE.md`, `docs/TOKEN-GUIDE.md`.
정답(ground truth, grep로 확정): /model·/effort·/fast 변경, MCP 연결/해제, /compact, 도구 정의 변경, 버전 업 후 첫 턴.

| 지표 | Baseline (통독+장황) | Optimized (grep+간결) | 차이 |
|---|---:|---:|---:|
| 실측 토큰(subagent) | 47,972 | 33,930 | **−29.3%** |
| 도구 호출 | 3 | 2 | −1 |
| 소요 시간 | 42.7s | 13.2s | **3.2× 빠름** |
| 정답 일치 | ✅ 정확 | ✅ 정확 | 동일(품질 유지) |
| quality/1k | 0.0208 | 0.0295 | **+42%** |
| OckScore(Q=1.0) | −16.57 | −13.80 | Optimized 우위 |

**해석**: 같은 정답을 내면서 토큰 29% 절감 + 3.2배 빠름 → "절약 vs 품질"은 가짜 트레이드오프임을 실증.
**주의(정직)**: 두 조건 모두 동일한 큰 고정 오버헤드(서브에이전트 시스템 프롬프트·도구 정의)를 포함 →
29%는 과제 자체 차이를 **과소평가**한다(순수 작업분 격차는 더 큼). Baseline의 추가 서술은 과제가
'목록'이었으므로 불필요한 장황함이며 quality/1k가 이를 벌한다.

### 실험 2 — 모델 라우팅: Haiku vs Opus, 기계적 과제 (2026-08-01)
과제: "measure.py의 module-level `def` 함수 이름·개수 나열"(정답 25개, grep 확정).
측정: 각 서브에이전트 task 트랜스크립트를 `python3 measure.py <task.output>`로 파싱(모델 필드 확인:
haiku-4-5 / opus-4-8 → 모델별 단가 자동 적용).

| 지표 | Haiku | Opus | 차이 |
|---|---:|---:|---:|
| 정답(25개) | ✅ 25/25 | ✅ 25/25 | 동일(품질 만점) |
| 실측 총 토큰 | 83,736 | 125,794 | Haiku −33% |
| 추정 비용 | $0.0632 | $0.4578 | **Haiku 7.2× 저렴(−86%)** |
| 캐시 적중률 | 46% | 47% | 유사 |

**해석**: 같은 완벽한 답에서 Haiku가 비용 7.2배 저렴 → "기계적 작업은 값싼 모델로" 라우팅 규칙 실증.
비용 격차(7.2×) > 토큰 격차(1.5×) 이유: Haiku 단가 5배 낮음 + 토큰도 33% 적음(Opus는 effort high로 thinking 多).
**주의**: *기계적* 과제 한정. 어려운 추론은 Haiku가 틀릴 수 있어(비대칭 오류) 라우팅 규칙은
"trivial→Haiku, hard→Opus + 실패시 상향". 이 실험은 trivial 절반을 검증.
교차검증: 하네스 subagent_tokens 비율(1.49×) ≈ measure.py 총토큰 비율(1.50×).

### 발견: measure.py는 task 트랜스크립트도 파싱 가능
`python3 measure.py <task.output>` 로 서브에이전트별 정밀 토큰·비용을 얻는다(모델 필드로 단가 자동).
→ 행위자별 분해를 task 파일 경로만 주면 수행 가능.

### 실험 3 — 라우팅 난이도 경계: 미묘한 버그찾기 (2026-08-01)
과제: `experiments/buggy_sample.py`의 `running_max` 버그 찾기(정답: `m=0` 초기화 → 음수 전용 입력에서
`[0,0,..]` 오답. ground truth는 실험자가 심음). 가설: Haiku가 실패, Opus 성공.

| 지표 | Haiku | Opus | 차이 |
|---|---:|---:|---:|
| 버그 발견(품질) | ✅ 정확(예시·수정 포함) | ✅ 정확 | 동일 |
| 실측 총 토큰 | 85,237 | 126,171 | Haiku −32% |
| 추정 비용 | $0.0414 | $0.3141 | Haiku 7.6× 저렴(−87%) |

**결과(정직): 가설 반증.** Haiku 4.5가 미묘한 음수-엣지케이스 버그를 Opus와 동일하게 정확히 잡음.
→ 이 실험은 "Haiku 실패"를 보여주지 못함. Haiku의 실패 경계는 예상보다 높음.
**함의**: 순진한 "추론=무조건 Opus"보다 더 공격적으로 Haiku 위임 가능. 단 경계 예측 불가 →
**실패시 상향 사다리(검증→실패시 상위 티어)**가 안전망인 이유. 진짜 경계를 찾으려면 더 어려운 과제 필요.

**3개 실험 종합**: 토큰 효율 기법(실험1, −29%)과 값싼 모델 라우팅(실험2·3, 7배 저렴)이 모두
**품질을 유지하면서** 절약. 세 번 다 "절약 vs 품질 = 가짜 트레이드오프"를 실측으로 확인.

### 실험 4 — 라우팅 경계 재시도: 생성형 구현 과제 (2026-08-01)
과제: 블라인드 스펙으로 `calculate(s:str)->int` 계산기 **구현**(찾기형 아닌 생성형으로 축 변경).
함정: unary minus/plus 중첩(`- -3`==3), **0쪽 절삭 나눗셈**(`-7/2`==-3, 파이썬 `//`는 -inf 방향이라 오답 유도),
연산자 우선순위, 중첩 괄호, 임의 공백. 오라클: `experiments/calc_tests.py`(25 케이스, 레퍼런스 자체검증됨).
두 모델 모두 레퍼런스 미공개, 코드만 회수 후 동일 스위트로 채점.

| 지표 | Haiku | Opus | 차이 |
|---|---:|---:|---:|
| 테스트 통과(품질) | ✅ 25/25 | ✅ 25/25 | 동일(만점) |
| 실측 토큰(subagent) | 32,583 | 44,286 | Haiku −26% |
| 추정 비용 | ~6.8× 저렴 | 기준 | base 5× × 토큰비 1.36× (실험2·3의 ~7×와 정합) |
| 도구 호출 | 0 | 1 | — |

**결과(정직): 가설 또 반증.** Haiku 4.5가 생성형 구현 + 복합 함정에서도 Opus와 동일하게 25/25.
찾기형(실험3)에 이어 생성형(실험4)에서도 경계를 못 드러냄 → Haiku 실패 경계는 이 난이도**보다도 위**.
구현 차이: Haiku는 `int(a/b)`(테스트 범위 2^31<2^53라 정확), Opus는 `abs()//abs()` 부호 복원 —
둘 다 0쪽 절삭 정확 구현. unary를 term 아래 계층에 배치한 것도 양쪽 정답.
**함의**: 단발 구현 과제로는 경계를 못 찾음. 다음은 축을 또 바꿔야 함 —
(a) **다단계 상태추적**(동시성/여러 제약 동시보유), (b) **긴 컨텍스트 종합**, (c) **반례 스스로 생성**이 필요한 과제.
라우팅 실무 결론은 불변: 경계가 예측불가·높음 → **공격적 Haiku 위임 + 실패시 상향 사다리**가 최적.
**메타(정직)**: 오라클 레퍼런스 최초 작성 시 실험자(나)가 `"" in "+-"`==True 함정에 빠져 IndexError →
자체검증(가장 값싼 오라클)이 즉시 포착·수정. "완료 선언 전 오라클 먼저" 규칙의 실사례.

**4개 실험 종합**: 토큰 기법(실험1 −29%) + 값싼 라우팅(실험2·3·4 ~7배)이 모두 품질 유지하며 절약.
Haiku 실패 경계는 4회 시도(기계적·찾기·미묘버그·생성구현) 전부에서 미검출 — 예상보다 훨씬 높음.

### 실험 5 — 외적 타당성: 프로젝트 유형 일반화 (2026-08-01)
동기: 실험 1~4는 전부 **이 툴킷 자기 파일**(measure.py 등)로만 검증 → "어떤 프로젝트든"을 주장 못 함(N=1 코드베이스).
설계: **구조가 다른 픽스처 3종**에 grep-first(optimized) vs 통독+장황(baseline) A/B. 모델 고정=Sonnet(변수=전략만).
정답은 전부 grep으로 확정. 픽스처는 함정 포함(async export, arrow-const, default export / interface·type alias / 데코레이터 자기정의).

| 픽스처 | 유형 | 크기 | 정답 | baseline 토큰 | optimized 토큰 | 절감 | 속도 | 품질 |
|---|---|---:|---:|---:|---:|---:|---:|---|
| webapp/src | TS 멀티파일 | ~74줄 | 9 export fn | 51,127 | 48,705 | −4.7% | 2.3× | 양쪽 ✅ |
| big_module.py | 대형 단일 | 679줄 | 9 @cached | 64,412 | 48,542 | **−24.6%** | 1.8× | 양쪽 ✅ |
| service.go | Go 단일 | 44줄 | 4 struct | 49,843 | 48,074 | −3.5% | 4.6× | 양쪽 ✅ |

**핵심 발견 1 — 품질은 전 유형에서 유지.** TS·Go·Python, 도메인 무관하게 grep-first가 정답을 100% 맞춤.
함정(async export/alias/데코레이터 자기정의)도 양쪽 조건 다 통과. **grep-first는 품질을 깎지 않는다**(전 유형 재현).

**핵심 발견 2 — 절감은 파일 크기에 비례(스케일 민감).** optimized 토큰이 3종 모두 ~48k로 수렴 →
이게 서브에이전트 **고정 오버헤드 바닥**(시스템프롬프트+도구정의). baseline은 그 위에 통독분을 더함:
순수 통독 페널티 = baseline − 48k 바닥 → 대형 **15.9k**, 소형 ~2k. 즉 %절감은 오버헤드에 희석되며,
**절대 절감은 읽었을 내용량에 비례**. 대형 파일 −24.6%는 실험 1(measure.py, 큰 파일) −29%와 정합 → 원 결과가 우연 아님.

**핵심 발견 3 — 장황함은 품질을 안 사고 노이즈를 추가.** baseline TS·Go 두 건에서 답을 세다 틀리고 자가정정
("총 8개… 정정 9개")하는 흔들림 발생. optimized는 깨끗. 여분 토큰이 정확도를 높이지 못함(오히려 실수 노출).

**일반화 검증 결론(정직):**
- ✅ grep-first + 간결 출력은 **프로젝트 유형·언어 불문 품질 무손실** — 결코 손해 안 봄.
- ✅ 이득은 **콘텐츠가 클수록 커짐**(대형 −25%, 소형 미미하나 음수 아님). "큰 파일·긴 로그일수록 grep-first" 규칙 실증.
- ⚠️ 소형 파일은 고정 오버헤드가 지배 → %는 작다. 그러나 **한 번도 느려지거나 틀리지 않음** → 무조건 적용이 안전.
- 라우팅(실험2~4)은 독립적으로 일반화됨 → 종합 처방: **grep-first 항상 + trivial/중간=Haiku + 간결출력 + 실패시 상향**.

**5개 실험 종합 처방 (어떤 프로젝트든):**
1. 탐색은 grep-first→offset/limit (품질 무손실, 큰 파일일수록 이득 ↑).
2. 기계적·표준 추론은 Haiku 위임(~7× 저렴, 실패 경계 매우 높음), 어려우면 상향 사다리.
3. 출력 간결화(장황함=노이즈, 품질 안 삼). 단 **필요한 추론 단계는 확보**(과삭제 금지).
4. 안정 컨텍스트 앞 고정→캐시 재사용, 세션 위생(작업경계 compact).

### 실험 6 — 계층형 하네스: 사다리 오케스트레이션 (2026-08-01)
설계: `harness/ladder_build.wf.js`(Workflow). Opus 아키텍트→Fable 카피→페이지별 [싸게 빌드→audit.mjs P1게이트→실패시 Opus 상향]→베이스라인(Opus 단독 3페이지). 시나리오=미니 쇼핑몰 3페이지 정적 프론트.
오라클=`frontend-design-review/references/audit.mjs`(36규칙, P1 위반 0이 게이트). 실측: 12에이전트, 에러0, 438초.

**품질 (audit P1/P2/P3, 낮을수록 좋음):**
| 페이지 | 하네스(티어) | 하네스 P1/P2/P3 | 베이스라인(Opus) P1/P2/P3 |
|---|---|---|---|
| 랜딩 | haiku→haiku ✅ | 0 / 2 / 0 | 0 / 6 / 1 |
| 상품목록 | sonnet→sonnet ✅ | 0 / 5 / 17 | 0 / 18 / 17 |
| 회원가입 | sonnet→sonnet ✅ | 0 / 1 / 12 | 0 / 1 / 12 |

품질: **게이트(P1) 양쪽 0. 하네스가 P2에서 오히려 우세**(랜딩 2<6, 상품목록 5<18). 상향 발동 0회(전부 첫 티어 통과).

**비용 (measure.py, 모델별 단가):**
| 항목 | 하네스 | 베이스라인 |
|---|---:|---:|
| 페이지 빌드 | haiku$0.15+sonnet$0.31+sonnet$0.38 = **$0.84** | opus 단독 **$1.40** |
| 아키텍트(opus) | $0.63 | — |
| 카피(fable) | **$0.99** | — |
| audit(haiku×3) | $0.14 | $0.20 |
| **합계** | **$2.60** | **$1.60** |

**결과(정직): 순비용 가설 반증 — 하네스가 1.6× 더 비쌈.** 단 분해하면 상반된 두 신호:
- ✅ **빌드 라우팅은 성공**: 값싼 티어로 3페이지 = $0.84 vs Opus $1.40 (**−40%**), 품질은 동등~우세.
- ❌ **오케스트레이션 오버헤드가 절감을 삼킴**: 아키텍트($0.63)+카피($0.99)+audit($0.14)=$1.76 고정비 > 베이스라인 전체.
  특히 **Fable 카피 $0.99**(마이크로카피에 과도 — fable 단가 높음). 3페이지론 고정비가 상각 안 됨.

**함의(실험 5와 정합 — 스케일 의존):** 사다리는 **페이지/과제 수가 많아 고정비가 상각될 때만** 순이득.
빌드당 −40%가 아키텍트+카피 고정비를 넘으려면 규모가 필요(대략 손익분기 ≥ 8~10페이지 추정).
소규모 단발 작업엔 단일 상위모델이 더 쌀 수 있다 → **"무조건 오케스트레이션"은 over-engineering.**
실무 교정: (a) 카피=Fable 대신 워커가 인라인(별도 에이전트 제거), (b) 아키텍트=필요시만, (c) audit 배치화,
(d) 사다리는 **대규모 반복 과제에 한정** 적용. 이 4개를 반영하면 소규모서도 근접/역전 가능(재실험 대상).

**6개 실험 종합:** 토큰기법(1)·라우팅(2~4)·일반화(5)는 품질 무손실 절약을 재현. 하네스(6)는
*빌드 라우팅은 유효하나 오케스트레이션 고정비 때문에 규모 임계 이상에서만 순이득* — 절약은 공짜가 아니라 **상각의 문제**.

### 실험 7 — Haiku 실패 경계: 다단계 상태추적 + 의미론 함정 (2026-08-04)
설계: 3단계 점진 탐색. **7a** L1~L5 순방향 시뮬레이션(10프로그램), **7b** L6 장기체인+L7 Python 의미론 함정(6프로그램),
**7c/7d** 실패지점 반복검증(L7c ×5, 힌트유무). 전부 Haiku vs Opus, effort:high, 결정론 오라클 채점.

**7a 결과**: Haiku 10/10, Opus 10/10. L5a(인터리브 상태머신 12스텝)+L5b(재귀+메모 스크램블)까지 양쪽 완벽.
순방향 시뮬레이션으로는 경계 미검출 — thinking 토큰이 무한 스크래치패드 역할.

**7b 결과**: Haiku 5/6, Opus 6/6. **최초 실패 발견.**
- L6a(40스텝), L6b(25스텝 동시대입), L7a(클로저), L7b(가변기본인자), L7d(복합슈퍼트랩): 양쪽 정답
- **L7c(튜플언패킹 LHS 평가순서)**: Haiku `[2,1,3,4,5]` ← FAIL, Opus `[2,2,1,4,5]` ← 정답
  코드: `a[0], a[a[0]] = a[a[0]], a[0]` — Haiku가 "swap"으로 패턴매칭, LHS 좌→우 중간변이 무시.

**7c 반복(힌트없음, N=5)**: Haiku **1/5**(20%), Opus 5/5(100%). 일관적 실패 확인.
**7d 반복(구체적 힌트, N=5)**: Haiku **5/5**(100%), Opus 5/5(100%). 프롬프트 보상 확인.

**확정 발견 3가지:**
1. **경계 위치 = 직관≠실제인 평가순서 의미론.** 연산 길이·복잡도가 아니라 패턴매칭이 틀리는 지점.
2. **확률적 실패**: 힌트 없이 Haiku 정답률 20%. 경계는 hard fail이 아니라 soft degradation.
3. **프롬프트 보상 가능**: 구체적 가이드("LHS 좌→우, 중간 변이 영향") 추가 시 100% 복원.

**실무 함의**: Haiku 위임 시 의미론 함정이 있는 작업은 프롬프트에 주의사항 명시.
사다리 규칙 교정: 오라클 기반 상향만이 아니라 **프롬프트 강화로도 보상 가능** — 상향 전 프롬프트 개선이 더 저렴.
오라클: `experiments/trace_oracle.py`(7a), `experiments/trace_oracle_b.py`(7b).
**7e 전 모델 비교(L7c, 힌트없음, N=3)**: Haiku 0/3, Sonnet 3/3, Fable 3/3, Opus 3/3.
경계는 **Haiku ↔ Sonnet 사이**. Sonnet($2)이 이 유형에서 최적점(Opus/Fable과 동일 정답률, 2~5배 저렴).
총 에이전트: 20(7a)+12(7b)+10(7c)+10(7d)+12(7e)=64, 토큰 ~1.6M.

**7개 실험 종합**: 토큰기법(1)·라우팅(2~4)·일반화(5)·하네스(6) 위에, 실험7이 Haiku 실패경계를 최초로 실증.
Haiku는 *순방향 시뮬레이션·Python 고전함정·장기연산*은 전부 정답이지만, *직관이 틀리는 평가순서 의미론*에서
확률적으로 실패. 다만 프롬프트 보상이 완전히 작동 → **사다리의 "상향" 단계 전에 "프롬프트 강화" 단계를 삽입**하는 것이
비용 최적. 최종 실무 처방: Haiku 공격적 위임 + 함정 주의사항 프롬프트 내장 + 오라클 검증 + 실패시 상향.

### 실험 8 — 사다리 실전 검증: 검증 기구 있는 실무 과제 3종 (2026-08-04)
동기: 실험 7이 Haiku 실패경계(의미론 함정)를 찾았지만, 실무 대부분은 **오라클(테스트·lint·schema)이 있는 과제**다.
"Haiku 시도→오라클 검증→실패시 상향" 사다리가 이런 조건에서 실제로 절감하는지 실측.

시나리오 3종(각 결정론 오라클 자체제작, `experiments/ladder_real/`):
- **A** 코드+테스트: `parse_duration(s)->int` 구현, 8케이스 함수 스위트
- **B** 버그+lint: `find_duplicates` 버그 수정, 기능테스트 + AST기반 lint(타입힌트·가변기본인자·bare except)
- **C** 데이터변환+schema: 지저분한 레코드 정규화, jsonschema 검증

방법: Haiku 1차 시도(Agent tool) → 오라클 채점 → Sonnet 베이스라인과 병렬 비교(에스컬레이션 필요성 자체도 관측 대상).

**결과: Haiku 3/3 PASS(1차, 에스컬레이션 0회), Sonnet 3/3 PASS.** 품질 동일.
| | 토큰 | 비용($1·$2 base) |
|---|---:|---:|
| Haiku | 86,009 | $0.086 |
| Sonnet | 132,669 | $0.265 |
| **비율** | **1.54×** | **3.09×** |

**함의**: 검증 기구가 있는 실무 과제(코드+테스트, 버그+lint, 변환+schema)에서 Haiku는 **1차 시도로 100% 통과**,
비용은 Sonnet 직행 대비 **3.09배 저렴**(토큰 자체도 1.54배 적음 — Sonnet이 더 장황하게 작성하는 경향 추가 관측).
사다리의 "실패시 상향" 비용은 이 3건에서 0 — 오라클 존재 과제의 실무 절감 가설이 최초로 정량 확인됨.
표본이 작아(N=3) 일반화엔 주의, 그러나 실험7(경계=의미론 함정)과 정합: 이 3과제 모두 "직관 그대로" 풀리는
구조라 Haiku 특유 실패모드에 안 걸림.

**8개 실험 종합**: 사다리 이론(실험1~7)이 처음으로 **실무형 태스크에서 실측 검증**됨. 종합 처방 갱신:
검증 기구 있는 과제(코드·데이터·lint) = Haiku 우선 디폴트, 의미론 함정 우려 과제 = Sonnet 우선,
불확실하면 Haiku 시도→오라클 실패시 프롬프트 강화→Sonnet.

#### 실험 8 표본 확대 (N=3→30, 2026-08-04)
동기: 원 실험은 과제당 1회 시도(3과제=3점)라 실패율 0%가 우연인지 구조적인지 구분 불가.
과제당 독립 Haiku 시도(콜드스타트, 별도 subagent) 10회씩 총 30회로 확대, 동일 오라클로 채점.

방법: `experiments/ladder_real/attempts_n10/{a,b,c}_haiku_NN.py` — 과제당 10개 독립 Agent 호출
(model=haiku, 매 호출 신선한 컨텍스트 — 배치 위임 금지 원칙 예외: 실패율 측정 실험은 독립성이
효율보다 우선). 채점기: `experiments/ladder_real/grade_n10.py`(결정론 오라클 재사용).

**결과: 30/30 PASS(실패 0건).** 실측 비용(이번 세션 `measure.py` 자동discovery로 확인):
서브에이전트 30개, 토큰 1,744,742, $0.5788(전부 Haiku) — 시도당 평균 약 $0.019.
Rule-of-three 근사로 진짜 실패율 상한 재추정: N=3일 때 0/3은 상한이 사실상 무의미(~100%)했으나,
N=30에서 0/30은 95% 신뢰수준에서 참 실패율 상한 **~10%**로 좁혀짐 — "직관대로 풀리는" 이 3과제
유형에서 Haiku 1차 통과가 우연이 아니라는 근거가 실험7 대비 훨씬 강해짐.

**에스컬레이션 비용은 여전히 미관측** — 실패가 0건이라 Sonnet 재시도가 발생하지 않음. 이는 결함이
아니라 결과: 이 과제 유형에서 사다리의 "실패시 상향" 분기가 실무 비용에 거의 기여하지 않는다는
뜻. 더 큰 N으로 합성 확대해도 실패를 하나도 못 만들면 정보 이득이 없으므로, 다음 단계는 표본을
더 늘리기보다 **실제 프로덕션 사용에서 발생하는 실패 사례를 수집**하는 쪽이 낫다(합성 벤치마크의
한계).

#### 실험 8 과제 다양성 확대 (D/E/F, 2026-08-04)
동기: 실험8(A/B/C)·표본확대(N=30) 모두 "직관대로 풀리는" 과제 유형만 검증. 사다리 처방이 다른
성격의 실무 과제에도 일반화되는지 확인 필요.

신규 시나리오 3종(각 결정론 오라클, `experiments/ladder_real/`):
- **D** 소규모 리팩터: 중복 if/elif/return 패턴 정리. 오라클=기능테스트 + AST 기반 elif 잔존 검사.
- **E** 설정 편집: 누락 필드만 기본값 채우기(기존값 덮어쓰기 금지). 오라클=jsonschema validate +
  기존값 보존 검사.
- **F** 멀티파일 컨텍스트 버그수정: 다른 모듈의 헬퍼 함수를 올바르게 재사용해야 풀리는 버그.
  오라클=기능테스트 + AST 기반 헬퍼 호출 여부 검사(재구현으로 우회 방지).

방법: 과제당 Haiku 독립 시도(콜드스타트) 5회씩 총 15회, 채점기 `grade_diversity.py`(결정론).

**결과: 15/15 PASS(실패 0건).** 실측 비용(`measure.py` 자동discovery, 이번 세션):
서브에이전트 15개, 토큰 872,196, $0.3279 — 시도당 평균 약 $0.022(A/B/C의 ~$0.019/시도와 비슷한
스케일). 리팩터·설정편집·멀티파일-재사용형 과제에서도 Haiku 1차 통과율 100% — 사다리 처방이
A/B/C(코드+테스트·버그+lint·변환+schema) 바깥 유형으로도 최소 이 정도 범위까지는 일반화됨을
시사. 단 N=5(과제당)로 작고, 여전히 "직관대로 풀리는" 구조(실험7의 의미론 함정 경계는 다른
실험이 이미 별도로 다룸) — 표본확대(N=30)와 동일한 한계 적용.

### 실험 9 — 오라클 없는 과제의 비대칭 교차검증 시도 (2026-08-04, 가설 기각)
동기: A~F는 전부 결정론 오라클(테스트·lint·schema)이 있는 과제. 오라클이 없는 프로즈/판단형
과제(기술설명·트레이드오프·코드리뷰·네이밍·우선순위판단)에도 사다리를 확장하려면 대체 검증이
필요 — 가설: "Haiku 생성 → Sonnet이 재생성 아닌 판정만(PASS/FAIL) → FAIL시만 Sonnet 재생성"이
비대칭 비용 구조(판정 <재생성)라 Sonnet 직행보다 쌀 것.

시나리오 5종(G1~G5, `experiments/ladder_real/task_g_oracle_less.py`): PUT/PATCH 설명, 동기/비동기
설명, SQL injection 코드리뷰, 함수명 리네이밍, 버그 우선순위 판단. 각각에 대해 (1) Haiku 생성
(2) Sonnet 판정(PASS/FAIL+한줄이유, 재생성 아님) (3) 비교용 Sonnet 직행 베이스라인. 채점은 사전
정의 키워드/정규식 루브릭(결정론, AI-YAGNI)으로 "필수 요소 포함 여부"만 확인.

**결과 1 — 판정: 5/5 PASS(에스컬레이션 0건).** Sonnet 판정자가 5건 모두 통과 처리.

**결과 2 — 루브릭 자체의 취약성 실측 확인**: G1은 루브릭이 True를 반환했지만 정규식이 의도와
다른 문장(PUT 관련 다른 문장의 "부분")에 우연히 매치된 것으로 확인(스퓨리어스 positive). G2는
Haiku 답변이 "블로킹/blocking" 대신 "대기·정지"로 개념은 맞게 설명했으나 정확 키워드가 없어
루브릭이 False 반환(false negative) — Sonnet 판정자는 이 경우를 PASS로 정확히 잡아냄. **결론:
키워드/정규식 기반 "약식 오라클"은 프로즈 채점에서 위양성·위음성 둘 다 실측으로 확인 —
코드 오라클(테스트·lint·schema)만큼 신뢰 불가. 오라클 없는 과제 검증은 근본적으로
"검증자를 검증할 방법이 없다"는 인식론적 한계에 부딪힘(사람이 최종 기준이 되거나, 신뢰도가
계속 한 단계씩 낮아짐).

**결과 3 — 비용: 가설 기각.** 실측(`measure.py`로 서브에이전트 15개 개별 세션 직접 집계):
| | 비용(5건 합) | 건당 평균 |
|---|---:|---:|
| Haiku 생성 | $0.3032 | $0.0606 |
| Sonnet 판정 | $0.3669 | $0.0734 |
| **사다리 합(생성+판정, 에스컬레이션 0건)** | **$0.6701** | — |
| Sonnet 직행 베이스라인 | $0.4310 | $0.0862 |
| **배율** | **1.55배(사다리가 더 비쌈)** | — |

**원인**: "판정 비용 < 재생성 비용" 가정이 틀림. 판정자에게 원 질문 + Haiku의 전체 답변을
컨텍스트로 줘야 하므로 입력 토큰이 신선한 베이스라인 생성보다 오히려 커짐(Haiku 답변이 장황할수록
악화 — G2에서 Haiku가 유독 장문 답변을 낸 게 대표적). 출력은 짧아도(PASS/FAIL+한줄) 입력이
이미 손해를 만회 못 함. 에스컬레이션이 0건이라 재생성 비용조차 발생 안 했는데도 이미 베이스라인보다
비쌈 — 만약 1건이라도 에스컬레이션됐다면 배율은 더 벌어졌을 것.

**처방 수정**: 오라클 없는 과제에 이 형태의 "비대칭 교차검증"은 **권장하지 않음**. 대신
(1) Tier 1(키워드/구조 체크)만으로 거를 수 있는 명백한 미완성 답변만 걸러내고 애매하면 그대로
통과시키거나, (2) 판정자 입력에서 후보 답변을 요약·절단해 판정 입력 비용을 억제하거나(단, 절단이
판정 정확도를 해칠 위험 있음 — 미검증), (3) 애초에 오라클 없는 과제는 Sonnet 직행을 유지(실험7
처방 그대로) — 이 셋 중 (3)이 지금까지 유일하게 실측으로 뒷받침됨.

#### 실험 9 후속 — 판정 입력 절단으로 재측정 (2026-08-04)
동기: (2)안(절단으로 판정 입력비용 억제)이 실제로 배율을 얼마나 좁히는지 미검증 상태였음 — 같은
G1~G5 판정을, Haiku 답변을 앞부분 150자로 고정 절단한 입력으로 재실행해 재측정.

**결과: 판정 5/5 여전히 PASS**(절단으로 뒷부분 근거·결론이 잘려나간 경우에도 판정자가 앞부분만으로
판단 — G3은 "해결책: 매개변수화된 쿼리" 문장이 통째로 잘렸는데도 PASS, 판정 근거가 내가 만든
엄격한 키워드 루브릭보다 관대함을 재확인).

| | 비용(5건) | 건당 평균 |
|---|---:|---:|
| Sonnet 판정(전체 컨텍스트) | $0.3669 | $0.0734 |
| Sonnet 판정(150자 절단) | $0.3152 | $0.0630 |
| **절단으로 판정 비용 절감** | **14%** | — |
| 사다리 합(Haiku생성+전체판정) vs 베이스라인 | 1.55배 | — |
| 사다리 합(Haiku생성+절단판정) vs 베이스라인 | **1.43배** | — |

**결론: 절단은 도움이 되지만 배율 역전을 못 뒤집음.** 절단으로 실제 절감된 건 14%뿐 — 토큰 수
자체도 거의 안 줄었음(263,649→219,489, ~17%). **원인 재확인**: 개별 서브에이전트 호출 비용의
대부분이 질문+후보답변 같은 "내용" 토큰이 아니라 **콜드스타트 고정 오버헤드**(시스템프롬프트·툴
스키마 로딩)에서 나옴 — 판정 대상 텍스트를 아무리 줄여도 이 고정비는 안 줄어듦. 이건 절단이
틀린 처방이 아니라 **애초에 "판정마다 새 서브에이전트를 띄운다"는 구조 자체가 고정비를 매번
새로 지불하는 설계**라는 뜻. 다음으로 시도해볼 만한 진짜 레버는 절단이 아니라 **(a) 여러 판정을
한 서브에이전트 호출에 배치**(고정비를 N개 판정에 분산) 또는 **(b) 서브에이전트 스폰 없이 메인
세션 안에서 인라인으로 판정**(고정비 자체를 회피) — 둘 다 미검증, 다음 세션 후보.
결론 갱신: 오라클 없는 과제는 여전히 **Sonnet 직행이 실측상 우위**(처방 (3) 유지).
